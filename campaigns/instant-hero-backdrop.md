# Instant hero backdrop

## Glossary

* **Hero backdrop** — the full-viewport backdrop image behind the Home page
  hero (`.page-backdrop` in `HomeLive`). The Library page's header band
  (`.page-atmosphere` in `LibraryLive`) draws from the same pool and the same
  serving path; "hero backdrop" covers both unless a phase says otherwise.
* **Master** — the original TMDB artwork file on disk. Backdrops are fetched
  at TMDB `original`, typically 3000–3840 px wide.
* **Derivative** — a width-bounded copy of a master generated by
  `MediaCentaur.ImageFiles.derivative/2` and requested with `?w=<px>`.
  The hero backdrop is the one surface that renders the master
  (`sized_image_url/2` with `:full_bleed`).
* **Live navigation** — a LiveView `navigate` between pages. The root layout
  and `app.js` survive it; the page DOM, including every `<img>`, is
  destroyed and rebuilt.
* **Sync decode** — `decoding="sync"` on in-flow images, mandated by
  UIDR-012 and enforced by MC0016: the frame waits for the decode so the
  page never paints a blank slot.
* **Decoded-bitmap cache** — the proposed JavaScript-owned cache of
  `ImageBitmap` objects keyed by image URL. It survives live navigation
  because it lives in `app.js`, not in the page DOM.
* **Media-center shell** — the dedicated browser instance that runs the
  app on the TV. Launched by `~/scripts/media-centaur/run` (outside this
  repo, not in dotfiles): a `--app` window, dedicated profile,
  XWayland for a stable window class, occlusion throttling disabled.

## Goal

Make the Home hero backdrop appear in the same frame the page mounts,
every time, at the master's full resolution. Today every return to Home
re-decodes a 3840×2160 JPEG and the backdrop visibly fills in after the
rest of the page; it is the one place in the app that reads as unstable.
The owner has declined trading pixels for speed, so the fix must keep the
look untouched.

## Status

Planning. Diagnosis complete and measured on the dev server (2026-09-06);
no code yet. Phase 1 is a launcher change outside the repo; Phase 2 is an
exploration gated on profiling in the real shell.

### What was measured (dev server, headless Chromium, 1920×1080 viewport)

Walk: Home → Discovery → Status → Home.

| Fact | Evidence |
|---|---|
| Bytes are cached on return | hero resource entry reports `deliveryType: "cache"`, 0 bytes transferred |
| Prefetch hints match the hero URL exactly | root layout emits the three `select_page_hero/2` backdrop URLs; hero `src` is byte-identical |
| Hero master is 3840×2160, 3.1 MB, baseline JPEG, 4:4:4, quality 90 | `identify -verbose` |
| Decode of the master, cache warm | ~50 ms per `img.decode()` |
| Decode of the `?w=1920` derivative | ~8 ms |
| Everything else Home decodes synchronously per visit | 51 sync images, 22.7 MP, ~70 ms summed |
| Hero-candidate master widths | 43 candidates: 12 × 3840, 16 × 3360, 1 × 3000, 11 × 1920, 3 × 1280 |

The element is rebuilt on every live navigation, and a 33 MB decoded
bitmap does not survive in the browser's decoded-image cache across four
poster-heavy pages, so each return pays the decode again. The hero fills
the viewport, which is why this one decode is the one the eye catches.

Headless numbers are software-rasterized; the real shell is GPU-composited
and measurements there are Phase 2's first job.

## Decisions made

* `2026-09-06` — **Bounded derivative declined.** Rendering the hero at
  1920 or a new 2560 rung removes most of the decode cost but upscales
  29 of 43 hero masters on the 4K panel. Owner wants the look untouched.
* `2026-09-06` — **Format change declined.** Baseline JPEG is already the
  cheapest mainstream format to decode; WebP is no better, AVIF is several
  times worse. Re-encoding the master at 4:2:0 would save roughly a third
  of the decode and still leave a visible pop. Not pursued.
* `2026-09-06` — **Browser switch is housekeeping, not a fix.** Vivaldi
  and Chromium share the engine; the hero behaves identically in both.
  Switching removes Vivaldi's three idle extension processes and tracks
  upstream sooner. It also gives Phase 2 a plain Chromium to profile.
* `2026-09-06` — **Decoded-bitmap cache is the candidate design.** Keep
  the decoded hero as an `ImageBitmap` in `app.js`, keyed by URL, and paint
  it onto a `<canvas>` in the hero slot from a hook. Adopt only if Phase 2
  profiling shows the gain in the real shell.

## Next steps

### Phase 1 — switch the media-center shell to Chromium

Out-of-repo change to `~/scripts/media-centaur/run`.

1. Replace `vivaldi-stable` with `chromium` and point `PROFILE_DIR` at a
   new dedicated profile (`~/.config/chromium-mediacenter`). Keep every
   existing flag: `--ozone-platform=x11`, `--class=media-centaur`, the
   three occlusion flags, `--app`, `--start-fullscreen`.
2. Add `--remote-debugging-port=<loopback port>` so Phase 2 can profile the
   real window with `chromium-probe` / CDP. Loopback only.
3. Verify the launcher contract: `hyprctl clients -j` reports
   `class == "media-centaur"` and `xwayland: true`; a second launch focuses
   instead of duplicating; cursor warp lands inside the window.
4. Verify the shell contract: play something in mpv, return, confirm the
   LiveView socket stayed alive (no stale pre-playback DOM); arrow keys and
   gamepad still drive the UI; the FLIRC remote's four bound buttons work.
5. Record the Chromium version in this file. Leave the Vivaldi profile in
   place until Phase 2 is decided, then delete it.

Rollback is the binary name and profile path.

### Phase 2 — explore the decoded-bitmap cache, with profiling

1. **Baseline in the real shell.** Against the Chromium instance from
   Phase 1, measure click-to-hero-paint on return to Home using an
   `elementtiming` attribute injected by a `MutationObserver` before first
   paint, plus a CDP trace (`cc`, `blink` categories) to read the image
   decode task duration for the hero. Repeat five times; record medians.
   This number is the bar the prototype has to beat.
2. **Prototype.** A JS module owning a small LRU of `ImageBitmap`s (cap by
   count, three entries ≈ 100 MB at 4K) and a `HeroBackdrop` hook on a
   `<canvas>` that replaces the `<img>` inside `.page-backdrop`. On
   `mounted`: cache hit → `drawImage` in the same task; miss →
   `fetch` + `createImageBitmap` → draw → insert. Canvas is a replaced
   element, so `object-fit: cover` and `object-position` carry over
   unchanged. The `?v=` availability bump already changes the URL, so the
   key is the invalidation.
3. **Warm the decode, not just the bytes.** Extend the existing warmup:
   the root layout already lists the page-hero URLs as `<link
   rel="prefetch">`; at idle, decode those same URLs into the cache so the
   first Home visit is instant too. `ArtworkWarmup.urls/0` stays the single
   source of the list.
4. **Profile after.** Same method as step 1. Also record renderer memory
   (`performance.measureUserAgentSpecificMemory` or the CDP `Memory`
   domain) with the cache full.
5. **Decide.** Adopt if the hero paints in the mount frame and memory is
   acceptable; otherwise record why and close the campaign with the
   sticky-element alternative explicitly declined.
6. **If adopted:** apply to the Library atmosphere band too; bun tests for
   the cache (keying, eviction, miss path); a LiveView test that the hero
   slot carries the URL the hook reads; a UIDR amending UIDR-012 for the
   one surface that no longer uses `<img>`; note in
   `docs/architecture.md` where the cache lives. No wiki change (nothing
   user-configurable).

### Open questions for Phase 2

* Does Chromium honour `decoding="sync"` for an 8 MP image on the GPU
  raster path, or does it fall back to async decode and paint the tile
  without the image first? The baseline trace answers this and explains
  the exact visual the owner sees.
* Canvas 2D colour handling: the master is sRGB and the panel is driven
  SDR for the shell, so no conversion is expected. Confirm the canvas
  output is pixel-identical to the `<img>` before adopting.
* First-visit behaviour on a cache miss: draw nothing until the bitmap is
  ready (the current visual), or keep the `<img>` as the miss path and only
  swap to canvas on a hit. Decide from the baseline numbers.

## Completion criteria

* The media-center shell runs Chromium with the launcher contract verified
  (class detection, no duplicates, socket survives mpv occlusion, remote and
  gamepad input work).
* A Phase 2 decision is recorded with before/after medians from the real
  shell, whichever way it goes.
* If adopted: Home and Library hero backdrops paint in the mount frame on
  return, at master resolution, with tests and the UIDR amendment landed.
* The Vivaldi media-center profile is removed.
